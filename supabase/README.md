# Catalog and stock receiving

Apply `migrations/202610310001_catalog_and_receiving.sql` in the intended project's Supabase SQL editor before using category creation or receiving. It adds the category registry, `cost_price` if missing, the stock receipt ledger, and the `pos_receive_stock` RPC. Existing `pos_products` and `pos_expenses` tables must exist; their existing column types, grants and RLS must allow the app's caller to update products and insert expenses.

The current POS has no sign-in screen and uses the public Supabase client. The new tables therefore grant `anon` and `authenticated` SELECT/INSERT, with no UPDATE/DELETE grants. The RPC uses `SECURITY INVOKER`: it does not bypass existing product/expense RLS. For a deployment with sign-in, narrow the new policies to the same tenant/user boundary as the existing POS tables before applying. Never use a service-role key in `NEXT_PUBLIC_*` variables.

Receiving locks the product row, calculates `total / quantity`, and commits stock, `cost_price`, receipt and optional expense in one transaction. Failures roll everything back. Retrying the same receipt UUID is idempotent; using that UUID with changed contents fails. No rounding is applied to stored unit cost; the UI rounds only the display.

Categories are stored separately so empty groups survive reloads, merged with existing product labels, and refreshed on focus / every 30 seconds. A creation updates all local filters immediately. A product's category is saved with the product. No sample products, receipts, sales or expenses are inserted by this migration.

Connection verification needs `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (or the legacy anon key) and HTTPS network access to the project's hostname. Test reads of `pos_products`, `pos_categories`, `pos_expenses`, `pos_cart_lines` and `pos_transactions`; check that the RPC appears in PostgREST's OpenAPI schema. Do not perform sample stock writes against a live store. Camera scanning requires HTTPS (localhost is supported for development), browser camera permission and a physical camera; the ZXing decoder supports QR and common product barcodes, including browsers without native BarcodeDetector. A keyboard-wedge scanner should send Enter or Tab after each scan. Search fields also accept explicit codes followed by Enter; scanners should not be used while editing quantities or payment amounts.
